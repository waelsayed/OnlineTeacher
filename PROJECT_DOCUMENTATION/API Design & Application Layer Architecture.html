القسم 1

1. Purpose

تهدف هذه الوثيقة إلى تحديد تصميم طبقة الـAPI وطبقة الـApplication في منصة Online Teacher، وتوضيح كيفية تحويل الـBusiness Use Cases والـDomain Rules إلى عمليات قابلة للتنفيذ من خلال الـASP.NET Core Web API.

تركز الوثيقة على: API Structure، Application Layer، Use Cases، Commands & Queries، DTOs، Validation، Authorization، Transactions، Error Handling، Pagination، Idempotency، Background Processing، Integration Boundaries.

ولا تهدف هذه الوثيقة إلى تحديد تفاصيل الـUI أو الـDatabase Schema التفصيلية.

القسم 2

2. Technology Stack

الـBackend الأساسي:

ASP.NET Core Web API PostgreSQL Entity Framework Core / Persistence Abstraction

مع إمكانية استخدام Redis عند الحاجة، Background Job Processing، External Video Provider APIs، External Storage Provider، Notification Providers. ويجب ألا تعتمد الـDomain Layer مباشرة على أي Technology-specific implementation.

القسم 3

3. Architectural Layers

يتم تقسيم الـBackend إلى طبقات واضحة:

Presentation / API ↓ Application ↓ Domain ↓ Infrastructure ↓ External Systems

Presentation / API: HTTP, Authentication, Authorization, Routing, Model Binding, Request/Response, API Errors.

Application: Use Cases, Commands, Queries, Orchestration, Transactions, DTOs, Application Validation.

Domain: Business Rules, Entities, Value Objects, Domain Services, Domain Events.

Infrastructure: PostgreSQL, EF Core, File Storage, Video Provider, Notification Providers, External Integrations.

القسم 4

4. API Boundary

الـAPI هي الـPublic Entry Point للنظام.

Client ↓ ASP.NET Core API ↓ Application Layer ↓ Domain

ولا يتم السماح للـClient بالتعامل مباشرة مع Database أو Domain Entities أو External Video Provider أو Storage Provider.

القسم 5

5. API Organization

يتم تنظيم الـAPI حسب الـDomain وليس حسب نوع الـHTTP Method.

/api/auth /api/students /api/teachers /api/platforms /api/courses /api/units /api/lessons /api/revisions /api/exams /api/homework /api/enrollments /api/follows /api/wallet /api/payments /api/refunds /api/coupons /api/posts /api/comments /api/messages /api/notifications /api/subscriptions /api/admin

والتقسيم النهائي يمكن تعديله أثناء التنفيذ حسب الـBounded Contexts.

القسم 6

6. Central Platform vs Teacher Platform

يجب التمييز بوضوح بين العمليات الخاصة بالـCentral Platform والعمليات الخاصة بالـTeacher Platform.

Central Platform Teacher Registration Teacher Subscription Teacher Activation Central Coupons Central Reports Platform Administration Teacher Platform Courses Students Enrollment Wallet Exams Homework Posts Teacher Coupons Teacher Reports

ولا يجب أن تختلط مسؤوليات الاثنين داخل نفس الـApplication Service بدون سبب.

القسم 7

7. Application Use Cases

كل عملية Business مهمة يتم تمثيلها كـUse Case. أمثلة: Enroll Student in Course، Activate External Payment، Create Coupon، Submit Exam، Submit Homework، Refund Purchase، Create Teacher Subscription، Publish Post، Extend Content Access.

الـController لا يحتوي على Business Logic لهذه العمليات.

Controller ↓ Command / Query ↓ Handler / Application Service ↓ Domain
القسم 8

8. Commands

الـCommand يمثل عملية تؤدي إلى تغيير في الـSystem State. أمثلة: CreateCourseCommand، EnrollCourseCommand، ActivatePaymentCommand، RefundPaymentCommand، CreateCouponCommand، SubmitExamCommand، SubmitHomeworkCommand، CreatePostCommand.

الـCommand لا يعيد Domain Entity مباشرة، بل يعيد Result أو Identifier أو DTO أو Operation Status بحسب العملية.

القسم 9

9. Queries

الـQuery لا يجب أن تغير حالة النظام. أمثلة: GetCourseQuery، GetStudentProgressQuery، GetTeacherStudentsQuery، GetWalletQuery، GetFinancialReportQuery، GetNotificationsQuery، GetTeacherPostsQuery، SearchTeachersQuery، GetExamResultQuery.

ويتم تصميم الـQueries بحيث تكون optimized للقراءة ولا تعتمد بالضرورة على نفس شكل الـDomain Entities.

القسم 10

10. DTOs

لا يتم expose الـDomain Entities مباشرة من الـAPI.

HTTP Request ↓ Request DTO ↓ Application ↓ Domain ↓ Response DTO ↓ HTTP Response

هذا يمنع تسريب تفاصيل الـDomain أو الـDatabase إلى الـAPI.

القسم 11

11. API Routing

يتم استخدام RESTful routing قدر الإمكان. لكن العمليات التي تمثل Business Actions يمكن التعبير عنها بوضوح.

GET /api/courses/{id} POST /api/courses PUT /api/courses/{id} DELETE /api/courses/{id} POST /api/courses/{id}/enroll POST /api/courses/{id}/archive POST /api/exams/{id}/submit POST /api/payments/{id}/activate POST /api/enrollments/{id}/refund

الهدف هو أن يكون الـAPI واضحًا وليس الالتزام الحرفي بـCRUD عندما لا يمثل الـBusiness Operation الحقيقي.

القسم 12

12. Teacher Platform Routing

يجب التعامل مع الـTeacher Platform من خلال Public Identity الخاصة بها: /{public-id}/{slug}. ويتم التحقق من PublicId وSlug معًا. الـSlug ليس هو الـIdentity. لا يسمح باستخدام Public ID صحيح مع Slug يخص Teacher Platform أخرى.

القسم 13

13. Authentication

Authentication مسؤول عن تحديد هوية الـUser. بعد Authentication يتم بناء User Context يحتوي على UserId وRole وPlatform Context وPermissions وStatus.

القسم 14

14. Authorization

Authorization في النظام لا يعتمد فقط على الـRole. يتم تطبيق Role + Dynamic Permissions + Resource Ownership + Platform Context.

Ahmed Role = Assistant Permission: ActivatePayment = true Permission: ExtendVideoAccess = false

وبالتالي لا يستطيع Ahmed تنفيذ Extend Video Access حتى لو كان Assistant آخر يستطيع ذلك.

القسم 15

15. Platform Context

كل Request يحتاج إلى معرفة الـContext الذي يعمل بداخله عند الحاجة: Central Platform Context أو Teacher Platform Context. ويجب منع User من الوصول إلى بيانات Teacher Platform لا يملك علاقة صحيحة بها.

القسم 16

16. Resource Authorization

حتى مع وجود Permission يجب التحقق من ملكية الـResource. مثال: Assistant A لديه Permission = Edit Course، لكن هذا لا يعني أنه يستطيع تعديل Course الخاص بـTeacher B. يجب التحقق من Permission + Course.PlatformId == CurrentPlatformId.

القسم 17

17. Student Access Rules

Request ↓ Authentication ↓ Platform Access ↓ Enrollment / Free Access ↓ Lesson Availability ↓ Prerequisites ↓ Expiration ↓ Attempts / Rules ↓ Allow / Deny

ولا يتم وضع هذه القواعد داخل الـController.

القسم 18

18. Enrollment

Enrollment عملية Business مهمة. عند Enrollment في Course:

Validate Course ↓ Validate Availability ↓ Validate Payment / Coupon / Free ↓ Create Enrollment ↓ Ensure Follow ↓ Create Financial Records ↓ Create Notification

يتم تنفيذ العمليات المطلوبة ضمن Transaction مناسبة.

القسم 19

19. Automatic Follow

عند إنشاء Course Enrollment: إذا كان Student لا يتبع Teacher يتم إنشاء Follow. ولا يحتاج الـClient إلى تنفيذ Follow بشكل منفصل. إذا كان الـStudent enrolled، لا يسمح له بإلغاء الـFollow الناتج عن Enrollment طالما أن الـEnrollment قائم.

القسم 20

20. Payment Activation

عملية الدفع في الإصدار الحالي ليست Payment Gateway. الـStudent يرسل بيانات التحويل.

Student ↓ Payment Request ↓ External Transfer ↓ Payment Proof ↓ Assistant ↓ Activation ↓ Wallet Transaction

الـAPI يجب أن تفصل بين Payment Request وPayment Activation لأن الـAssistant هو الذي يعتمد العملية.

القسم 21

21. Wallet Transactions

أي تعديل على Wallet يجب أن ينتج عنه Ledger Transaction. أمثلة: Deposit، Purchase، Refund، Adjustment، Coupon Credit. لا يسمح للـApplication Layer بتعديل Balance بطريقة غير مرتبطة بسجل مالي.

القسم 22

22. Purchase Transaction

عملية شراء Course يجب أن تكون Atomic قدر الإمكان.

Validate Price ↓ Validate Wallet Balance ↓ Create Purchase ↓ Debit Wallet ↓ Create Enrollment ↓ Ensure Follow ↓ Notify Student

إذا فشلت خطوة أساسية يتم Rollback للعملية.

القسم 23

23. Insufficient Balance

إذا كان Wallet Balance أقل من Required Amount فالشراء يفشل. ولا يتم إنشاء Enrollment أو خصم جزئي أو Negative Balance. ويتم إرجاع Error واضح للـClient.

القسم 24

24. Coupon Application

Coupon Exists ↓ Not Expired ↓ Not Consumed ↓ Belongs to Current Target ↓ Valid for Current Plan / Value ↓ Consume

Coupon الخاص بالTeacher Student يكون مخصصًا لطالب محدد. Coupon الخاص بالCentral Platform يكون مرتبطًا بالـTeacher Subscription Plan.

القسم 25

25. Refund Application Flow

Validate Refund Eligibility ↓ Calculate Refund Amount ↓ Deactivate / Unenroll Content ↓ Create Refund Record ↓ Record External Refund ↓ Update Financial History ↓ Notify Student

إذا كان الـRefund خارجيًا، لا يعاد المبلغ إلى Student Wallet تلقائيًا.

القسم 26

26. Exam Submission

Open Exam ↓ Create Attempt ↓ Start Timer ↓ Answer Questions ↓ Submit ↓ Validate Attempt ↓ Grade Objective Questions ↓ Store Result ↓ Notify Student ↓ Notify Parent if applicable

بعد Submit لا يتم السماح بتعديل الإجابات في الـOnline Exam.

القسم 27

27. Exam Time Limit

الـTimer يعتمد على وقت بدء الـAttempt المسجل في Server، ولا يعتمد على Clock الموجود على جهاز الطالب.

Attempt.StartedAt + Exam.Duration = Attempt.Deadline

وبالتالي انقطاع الإنترنت أو إغلاق الجهاز لا يؤدي إلى تمديد الوقت.

القسم 28

28. Homework Submission

الإصدار الأول يدعم File-based Submission.

Upload File ↓ Validate File ↓ Store File ↓ Create Submission ↓ Notify Teacher

يمكن دعم أنواع أخرى مستقبلًا دون تغيير الـApplication Architecture الأساسية.

القسم 29

29. Video Provider Abstraction

لا يتعامل الـApplication Layer مباشرة مع Video Provider معين. يتم تعريف Interface مثل IVideoProvider ويتم تنفيذها في Infrastructure. أمثلة العمليات: GetVideoProgress، GetPlaybackSession، GetAttempts، GetExpiration. وبالتالي يمكن تغيير Video Provider مستقبلًا.

القسم 30

30. Video Access

Validate Student ↓ Validate Content Access ↓ Validate Expiration ↓ Validate Attempts ↓ Request Provider Session ↓ Return Playback Information

ولا يتم كشف credentials الخاصة بالـVideo Provider للـClient.

القسم 31

31. File Management API

يتم فصل File Metadata عن Storage. مثال: POST /api/files ثم يتم استخدام File Reference داخل Lesson وHomework وPost وPayment وTeacher Profile. الـStorage Provider يمكن تغييره دون تعديل الـDomain.

القسم 32

32. Notifications

الـNotification Creation يجب ألا تجعل الـBusiness Operation تعتمد بشكل مباشر على إرسال Push/Email/SMS.

Exam Submitted ↓ Create Notification Event ↓ Notification Processing ↓ Push / Email / In-App

وهذا يسمح بإضافة Notification Channels مستقبلًا.

القسم 33

33. Background Processing

العمليات التي لا تحتاج إلى إكمالها قبل HTTP Response يمكن تنفيذها بشكل asynchronous/background. مثل Notifications وReport Generation وAudit Processing وVideo Synchronization وFile Processing وEmail Sending. لكن العمليات المالية الأساسية لا تعتمد على Background Job وحده.

القسم 34

34. Error Handling

يجب استخدام Error Response موحد.

{ code: "INSUFFICIENT_BALANCE", message: "Wallet balance is insufficient." }

ويتم الفصل بين Business Error وValidation Error وAuthentication Error وAuthorization Error وNot Found وConflict وSystem Error. ولا يتم إرجاع Exception Details الداخلية للـClient.

القسم 35

35. Validation

يتم تنفيذ Validation على أكثر من مستوى: API Validation للتحقق من شكل البيانات، Application Validation للتحقق من شروط الـUse Case، Domain Validation للتحقق من Business Invariants.

API: Amount > 0 Application: Wallet belongs to Student Domain: Wallet cannot become negative
القسم 36

36. Concurrency

العمليات الحساسة يجب أن تراعي Concurrent Requests، خصوصًا Wallet وCoupon Consumption وEnrollment وExam Attempt وSubscription Activation. مثال: إذا حاول الطالب استخدام نفس Coupon مرتين في نفس الوقت، يجب أن ينجح Request واحد فقط.

القسم 37

37. Idempotency

العمليات الحساسة التي يمكن إرسالها أكثر من مرة يجب أن تدعم Idempotency عند الحاجة، خصوصًا Payment Activation وPurchase وRefund وCoupon Consumption وExam Submission. مثال: إذا أعاد Client إرسال Purchase Request بسبب Network Timeout، لا يجب خصم المبلغ مرتين.

القسم 38

38. Pagination

الـAPI تستخدم Pagination للبيانات الكبيرة مثل Students وPosts وComments وNotifications وTransactions وAudit Logs وSearch Results. الـPagination ليست بالضرورة Page Numbers. يمكن استخدام Cursor / Continuation Token خصوصًا في الـFeed والـSocial Content.

القسم 39

39. Search

Search APIs تدعم حسب الحاجة: Teacher، Subject، Grade، Study Type، Course، Post. بالنسبة للـCentral Platform يتم دعم Teacher Discovery بناءً على Grade وStudy Type وSubject وTeacher Name / Platform Name. والـAcademic Year الحالية هي الـdefault context.

القسم 40

40. Reporting APIs

الـReports يتم التعامل معها كـQueries متخصصة. أمثلة: GetTeacherStudentsReport، GetTeacherSalesReport، GetTeacherPaymentsReport، GetTeacherCouponsReport، GetTeacherRevenueSummary، GetCentralTeachersReport، GetCentralSubscriptionRevenue. ويجب عدم إعادة استخدام Entity Queries البسيطة لبناء Reports معقدة إذا كان ذلك سيؤثر على الأداء.

القسم 41

41. Audit Logging

كل Application Operation مهمة تنتج Audit Event. أمثلة: PaymentActivated، CourseArchived، AssistantPermissionChanged، CouponConsumed، RefundApproved، SubscriptionActivated، PostDeleted. ويتم تسجيل Actor وPlatform وAction وEntity وEntityId وTimestamp وIP وStation وDevice.

القسم 42

42. API Security Pipeline

HTTP Request ↓ HTTPS ↓ Authentication ↓ User Status ↓ Platform Context ↓ Authorization ↓ Validation ↓ Application Use Case ↓ Domain Rules
القسم 43

43. User Status Enforcement

إذا كان User Blocked أو Deactivated أو Suspended يجب ألا يستطيع تنفيذ العمليات المحمية حتى لو كانت لديه Permissions محفوظة. وبالتالي: Active + Permission + Valid Context = Allowed.

القسم 44

44. API Versioning

يجب تصميم الـAPI بحيث تسمح بإصدارات مستقبلية. الاتجاه المبدئي: /api/v1/... ويتم الانتقال إلى /api/v2/... عند وجود Breaking Changes حقيقية. ولا يتم إنشاء Version جديد لمجرد إضافة Field غير مؤثر.

القسم 45

45. Dependency Injection

يتم استخدام ASP.NET Core Dependency Injection لربط Application Interfaces مع Infrastructure Implementations. مثل IVideoProvider وIFileStorage وINotificationService وIEmailService وIUnitOfWork. ولا يتم إنشاء Infrastructure Services مباشرة داخل الـDomain.

القسم 46

46. Transaction Boundary

الـTransaction يتم تحديدها حسب الـUse Case وليس حسب كل Repository Call. مثال: Enroll Course قد تحتاج Transaction تشمل Purchase وWallet Debit وEnrollment وFollow. بينما Query بسيطة لا تحتاج Transaction كتابة.

القسم 47

47. Domain Events

يمكن استخدام Domain/Application Events للأحداث المهمة. أمثلة: CourseEnrolled، PaymentActivated، ExamSubmitted، ExamGraded، HomeworkSubmitted، CouponConsumed، RefundCompleted، SubscriptionActivated. وتستخدم هذه الأحداث لربط الـDomains دون coupling مباشر.

القسم 48

48. API Documentation

يجب توثيق الـAPI باستخدام OpenAPI/Swagger. كل Endpoint يجب أن يوضح Purpose وAuthentication وAuthorization وRequest وResponse وValidation Errors وBusiness Errors وHTTP Status Codes.

القسم 49

49. Observability

يجب أن تدعم طبقة الـApplication والـAPI: Structured Logging، Correlation ID، Request Tracing، Error Tracking، Performance Metrics. خصوصًا للعمليات الحساسة مثل Payment وPurchase وRefund وExam وVideo Access وAuthentication.

القسم 51

51. Architectural Rules

  1. الـController لا يحتوي Business Logic.
  2. الـDomain لا يعتمد على ASP.NET Core أو EF Core.
  3. لا يتم إرجاع Domain Entities مباشرة من الـAPI.
  4. الـPermissions Dynamic وليست Hard-coded داخل Role.
  5. كل Resource يتم التحقق من Platform Ownership الخاصة به.
  6. العمليات المالية يجب أن تكون Atomic وقابلة للتتبع.
  7. لا يتم السماح بـNegative Wallet Balance.
  8. Coupon Consumption يجب أن يكون آمنًا ضد Concurrent Requests.
  9. Video Provider يتم التعامل معه من خلال Abstraction.
  10. File Storage يتم التعامل معه من خلال Abstraction.
  11. Audit Trail لا يتم حذفه مع حذف الـBusiness Entity.
  12. Student Identity واحدة على مستوى النظام.
  13. Teacher Platform هي حدود أساسية لعزل بيانات Teacher.
  14. Central Platform لا تتملك Student Wallet الخاصة بالـTeacher Platform.
  15. لا يتم إنشاء Role جديدة لمجرد اختلاف Permissions بين Users.
  16. الـPublic ID والـSlug يتم التحقق منهما معًا في Teacher Platform Routing.
  17. العمليات التي يمكن تكرار Request لها يجب أن تراعي Idempotency.
  18. الـQueries الكبيرة يجب أن تكون optimized للقراءة.
  19. العمليات غير الضرورية لإتمام الـRequest يمكن تنفيذها في Background.
  20. أي قرار جديد يجب أن يحافظ على حدود الـBounded Contexts.
القسم 52

52. Conclusion

طبقة الـAPI في Online Teacher ليست مجرد CRUD فوق PostgreSQL. هي طبقة تنفيذ للـBusiness Domains والـUse Cases المحددة في الوثائق السابقة، مع الحفاظ على الفصل بين Central Platform وTeacher Platform وStudent وAcademic Content وFinancial Domain وSocial Domain وCommunication وSecurity.

ويتم بناء الـApplication Layer بحيث تكون قابلة للتوسع وإضافة مزودي الفيديو والتخزين والدفع والإشعارات مستقبلًا دون إعادة تصميم الـCore Domain.
